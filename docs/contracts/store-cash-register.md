# Store cash register

Store Console exposes a small manual cash register to active members with `store:cash_entry:read` for the selected store. Recording also requires `store:cash_entry:create`. Store and actor come from the route and authenticated session, not the input. Run the Accounting authorization seed and assign `store_cash_reader` or `store_cash_recorder` in the appropriate Store scope; the seed creates no assignments.

The register is separate from the company general ledger. The Store Console is append-only. Entries are recorded with the existing Store staff command receipt; repeating the same command and normalized payload returns the existing entry, while changing the payload with the same key conflicts. No payment, inventory movement, or accounting posting is triggered. The page keeps the same command ID on an uncertain in-page retry; if the page is closed, inspect the register before re-entering the transaction.

Finance users with `cash_record` can correct an unlinked entry in Admin using `POST /commands/correct-cash-entry` with `id`, the `cash_version` from the list, `date`, `category`, `amount`, `note`, `reason`, `command_id`, and purchase fields `item`, `quantity`, and `unit` when applicable. The book lock serializes corrections with draft generation and unbinding. A stale version or any linked journal (including voided drafts) blocks correction. The original identity, store, recorder, and currency are preserved, and the Finance audit keeps before/after values and the reason.

Finance can void an entry instead of deleting it. `POST /commands/void-cash-entry` (`id`, `reason`, `command_id`) marks it voided and preserves the record, actor, and reason in the Finance audit. Voided entries disappear from the Store Console register and monthly totals, and they cannot be corrected or used to generate a draft. A linked journal blocks voiding while it is a draft or posted; after the journal is voided, the cash entry may also be voided. Replaying the same command returns the same result, while a second, different void conflicts. Admin lists keep voided rows with their status for traceability.

Admin **Finance → Store cash entries → Record cash entry** records to the same register. `ROLE_ADMIN` or a global `accounting_cash_recorder` assignment can use `POST /cash-entries` under the selected [Finance book prefix](accounting.md). The Finance workspace returns `cash_stores` (UUID, name, code and currency) for eligible recorders. The endpoint accepts `store_uuid`, `command_id`, `date`, `direction`, `category`, `amount`, and optional `note` and `metadata`. The server requires a store bound to the selected book and uses the authenticated Finance actor and the store's currency. Replay is scoped to the actor and store. It returns the entry ID and never creates a draft, even when a category mapping exists. Recording does not require a posting period or grant permission to draft or post journals. Run the Accounting authorization seed again before assigning the new Finance role.

The frontend controls the category-specific form. The backend accepts version 1 metadata with optional `reference` and bounded `extra` strings. Purchase metadata must also supply item name, decimal quantity and `g`, `kg`, `ml`, `l`, or `piece` (whole items only). Item name and reference are display values, not a catalog association or proof of an external purchase. Extra fields do not enter calculations.

The backend calculates purchase price from the whole entry's amount and quantity, converting kg to g and L to mL. Amounts and totals are exact string minor units at the Store console's existing two-decimal scale. Unit-price results are decimal strings rounded half-up to eight places in major units. The monthly totals are split by currency, direction, and category and are independent of the current entry page. They describe recorded cash activity and purchase prices, not stock consumption, cost of goods sold, or margin.

There is currently **no source purchase order model connected to this workflow**, so records are explicitly marked manual. A future import must use a trusted confirmed purchase source, stable source identity, and deduplication/adjustment rules; an entered text reference is not an import key. There is no automatic synchronization with the company ledger. Finance can explicitly [generate a journal draft](accounting.md) from a cash entry; recording one in Store Console never creates a journal on its own.
