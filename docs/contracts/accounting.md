# M1 manual accounting contract

**Status:** M1 implemented in `business/`. Verified in isolated backend integration tests and a MySQL 8.4 migration/concurrency harness. Interactive production rollout is not established. [M2 source integration](../design/accounting.md#m2-opt-in-source-integration) is not implemented.

- Finance uses the existing Admin session. `ROLE_ADMIN` has all Finance capabilities by default and can use `/api/v1/manage/accounting/*`. `/api/v1/finance/*`, used by the Finance page, also permits authenticated non-admin users with an active global Finance `read` grant and the grant for the requested operation. A Store grant is not a Finance grant. Navigation does not authorize access.
- The book is a singleton, configured explicitly and fixed after initialization. Periods are local calendar months. A posted opening journal or an audited zero-opening approval is required before posting ordinary entries. No balance or chart is automatically initialized.
- Standard EasyAdmin resources are `GET|POST /ledger-accounts`, `GET|PUT /ledger-accounts/{code}`, `GET|POST /accounting-periods`, and `GET /accounting-periods/{month}` under the Manage and Finance prefixes above. List responses carry the standard paginator and support `page`, `limit`, and single-column `@order` restricted to displayed fields; accounts also accept literal `q` search. Account codes and period months are stable record IDs. Creation rejects duplicates; account update cannot rename the code or create a missing account. Writes require `configure` and call the ledger command service, including its audit and transaction rules. Deletion and generic period updates are not exposed; initialization, posting, reversal, and period state changes remain explicit commands. The existing `save-account` and `add-period` command endpoints retain their behavior.
- Draft changes are optimistic and only the current revision may be updated, voided, or posted. Posting requires positive exact minor-unit lines with matching nonzero totals, eligible accounts, and an open period. A single book lock serializes mutations. A posted journal is immutable via application APIs. An exact opposite journal corrects a manual posting at most once; it never reverses an opening, another reversal, or a money movement.
- Retriable commands take a UUID and return the stored result on exact replay by the same authorized actor. Reusing a key with a different normalized request is a conflict. An independent reversal with the same date and reason returns the existing reversal; a different date or reason conflicts.
- Reports read only posted lines. Amounts are strings in integer minor units, including CSV; account ledgers include running balances. Posted financial pages use a cutoff, which must be carried with the same filters when requesting subsequent report pages or exports. The journal register includes mutable drafts and is a live paginated read, not a snapshot.
- Journal list and detail use the standard read ViewMixins with Finance authorization and fixed projections. The register accepts `from`, `to`, `state`, `account`, and `page`; generic query and expansion directives are not supported on journal endpoints. No generic journal write actions are registered.
- Evidence text and the command audit require `audit`; generic HTTP audit retains transport metadata rather than financial payloads. Successful Finance responses are private and non-cacheable.
