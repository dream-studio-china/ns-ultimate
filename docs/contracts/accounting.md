# M1 manual accounting contract

**Status:** M1 implemented in `business/`. Verified in isolated backend integration tests and a MySQL 8.4 migration/concurrency harness. Interactive production rollout is not established. [M2 source integration](../design/accounting.md#m2-opt-in-source-integration) is not implemented.

- Accounting uses the existing Admin session. `ROLE_ADMIN` has all Finance capabilities by default and can use `/api/v1/manage/accounting/*`. `/api/v1/finance/accounting/*` also permits authenticated non-admin users with an active global Finance `read` grant and the grant for the requested operation. A Store grant is not a Finance grant. Navigation does not authorize access.
- Each store can have one independent book, configured explicitly and fixed after initialization. The original book (`1`) remains unassigned; migration does not move or duplicate any entries. Periods are local calendar months. Each book has its own chart, opening position, posting sequence, cutoff, and command receipts. A posted opening journal or an audited zero-opening approval is required before posting ordinary entries. No balance or chart is automatically initialized.
- Headquarters creates store books through `POST /api/v1/finance/accounting/books` with `store_uuid` and lists them through `GET /books` under the same prefix. Selecting a book in Admin changes the workspace and ledger resource prefix to `/api/v1/finance/accounting/book/{bookId}`. Existing unscoped ledger operations continue to target book `1`. Global Finance capabilities also apply to selected books; there is no cross-book reporting.
- `/api/v1/store/{scopeId}/accounting/` exposes read-only `workspace`, `journals`, `journals/{id}`, `reports/{kind}` and `reports/{kind}/csv`. The server checks active Store membership and `store:accounting:read` through existing Store authorization, then resolves the bound book. There is no client supplied book override. Store detail responses omit evidence, attachments and metadata; Store readers have no access to ledger commands or audit. The Store Console exposes the journal register, line details, trial balance and trial CSV.
- Standard EasyAdmin resources under the Manage and Finance prefixes above:

  | Resource | Endpoints | Writes |
  | --- | --- | --- |
  | Book | `GET\|POST /books`, `GET /books/{id}` | `POST` initializes a store book (`configure`), or the legacy book if no store is given. An identical repeat is a no-op; different parameters conflict. No update. |
  | Accounts | `GET\|POST /ledger-accounts`, `GET\|PUT /ledger-accounts/{code}` | `configure`. Creation rejects duplicates; update cannot rename the code or create a missing account. |
  | Periods | `GET\|POST /accounting-periods`, `GET /accounting-periods/{month}` | `POST` adds a month (`configure`). |
  | Journals | `GET\|POST /journals`, `GET\|PUT /journals/{id}` | `draft`. `POST` only creates a draft; `PUT` only revises the current revision of a draft. Both run the `create-draft`/`update-draft` commands, so the book lock, revision check, validation, and audit apply. An optional `command_id` on `POST` makes an exact retry return the same draft; without one the create is not replay-protected. |
  | Audit | `GET /audit`, `GET /audit/{id}` | Read only; requires `audit`. |
  | Reports | `GET /reports/{trial,balances,ledger}`, `GET /reports/{kind}/csv` | Read only. |

  Lists return the standard `data` rows and `paginator` (`total`, `page`, `limit`, `pages`, `has_previous`, `has_next`); `limit` is at most 300. Account and period lists accept single-column `@order` restricted to displayed fields, and accounts accept literal `q` search. The journal register accepts `from`, `to`, `state`, and `account`. Generic EasyAdmin query and expansion directives such as `@filter` are rejected. Account codes, period months, book and journal IDs are stable record IDs. Deletion, batch writes, and generic updates of posted journals or period state are not exposed; posting, voiding, reversal, zero-opening approval, and period lock/reopen remain explicit commands at `POST /commands/{action}`, which also keep serving `initialize`, `save-account`, `add-period`, `create-draft`, and `update-draft` unchanged.
- Draft changes are optimistic and only the current revision may be updated, voided, or posted. Drafts may include up to 20 HTTP(S) attachment reference URLs; those references are returned only to users with `audit`. The Admin form uploads files through the signed-in user's media endpoint and stores the resulting URLs; the ledger itself does not upload, store, or proxy files, and it does not control access to the referenced files. Posting requires positive exact minor-unit lines with matching nonzero totals, eligible accounts, and an open period. A single book lock serializes mutations. A posted journal is immutable via application APIs. An exact opposite journal corrects a manual posting at most once; it never reverses an opening, another reversal, or a money movement.
- Journal create and update (resource or command) accept an optional `metadata` JSON object, separate from evidence and attachments, up to 8 KiB when compactly encoded. Omission on update preserves the existing object; `{}` clears it. An authorized journal detail returns `{}` when none is set. Metadata is not copied to a reversal or included in the register, reports, exports, or audit payloads. Use strings for external IDs and do not store secrets or raw provider payloads.
- Retriable commands take a UUID and return the stored result on exact replay by the same authorized actor. Reusing a key with a different normalized request is a conflict. An independent reversal with the same date and reason returns the existing reversal; a different date or reason conflicts.
- Reports read only posted lines. Amounts are strings in integer minor units, including CSV; account ledgers include running balances. Each report page also returns `report` with `kind`, `cutoff`, `currency`, `scale`, and the ledger `opening` balance or trial `totals`. A request without `cutoff` captures the current posting cutoff; subsequent pages and the CSV export must send that cutoff with the same filters to read the same snapshot. The journal register includes mutable drafts and is a live paginated read, not a snapshot.
- Journal list and detail use the standard read ViewMixins with Finance authorization and fixed projections; register rows include `revision` for explicit commands.
- Evidence text, attachment references, journal metadata, and the command audit require `audit` to read; generic HTTP audit retains transport metadata rather than financial payloads. Successful Finance responses are private and non-cacheable.
