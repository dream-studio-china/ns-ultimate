# Generic admin-agent operations

## Ownership and adapters

`apps/admin-agent/` owns the generic browser assistant and Symfony operation backend. One app-owned `AgentOperation` entity/table stores proposals and receipts for all explicitly registered mutation adapters. Unknown and duplicate adapter keys fail closed; input never resolves PHP classes or arbitrary URLs. No core files are changed.

Integration explicitly wires the app namespace, services, routes, Doctrine mapping, migrations, tests and Docker inclusion. It supplies `ActorIdentityProvider` using the authenticated account UUID and explicitly selects app-owned host mutation adapters. The app's generic service import excludes `src/Adapter/`, so unselected host adapters are not enabled implicitly. Adapters implement `MutationAdapter`: `entityKey`, `authorize`, side-effect-free `prepare`, and transactional `execute`. Target/action/field permissions, exact lookup, canonical snapshots, agent-specific restrictions, target locking, mutation and read-back verification belong to adapters, reusing existing domain entities and validation without adding agent code to business modules or core. The app owns account binding, expiry, operation locking, idempotency and receipts. Adapters are trusted application code and must not perform non-transactional external side effects under this contract.

`apps/admin-agent/adapters/ns-ultimate/admin/mutation-capabilities.mjs` supplies capability descriptions through the integration host to the generic fixed-route transport. The adjacent `preview-policy.mjs` retains a local Counter.name preview policy, but the preview is not authorization and does not replace the confirmed mutation flow. The model tool `prepare_record_change` only prepares proposals; there is no commit tool. Full differences and operation IDs stay inside the host/UI boundary rather than entering tool messages. Proposed values already present in chat are still sent to the configured provider. Confirmation cards display field values as text, never rendered HTML.

Content is explicitly registered by `integration/backend/config/services.yaml`; the remaining business adapters are explicitly registered by `apps/admin-agent/backend/config/services.yaml`. Excluding adapter auto-discovery does not remove explicit registrations.

## Business capability packages

All packages require `ROLE_ADMIN` and retain single-record preparation, explicit UI confirmation, transactional execution, conflict checking and metadata-only receipts. Approval of a business package does not permit arbitrary fields, URLs or bulk operations. Registered actions and their per-action rules are declared in the host policy, not inferred from OpenAPI or knowledge text.

| Entity | Actions | Field boundary |
| --- | --- | --- |
| Content | Create, update, delete | Existing `title`, `body`, `category`, `tags`, schema-bounded `metadata`, `sortOrder` policy remains unchanged. |
| Counter | Create, update, unreferenced delete | `code`, `name`, `capacity`, `sort`, `enabled`; exact active `storeUuid` on create only. No metadata edits or store reassignment. |
| Store | Update only | `name`, explicitly schema-validated partial `contact` and `address`; no arbitrary nested keys, settings, timezone, currency or lifecycle changes. Existing private contact/address values are redacted from previews. |
| Category | Create, update, unreferenced delete | `name`, `slug`, `description`, `parent`, `sortOrder`, `enabled`; scope-safe acyclic hierarchy and unique slug. |
| Tag | Create, update, unreferenced delete | `name`, `slug`, nullable `color` (`#RRGGBB`); unique slug. |
| ProductCategory | Create, update, unreferenced delete | Category fields plus owning `store` on create only; parent hierarchy must retain store/global scope. |
| Product | Create, update | `name`, `description`, `category`, `sortOrder`, `recommendationLevel`, `status`, `isSoldout`; owning `store` on create only, with global scope represented by null. Category must be enabled and match scope. |
| Specification | Create, update | `productId`, `name`, `price`, `status`, `sort`; existing Product scope is immutable and must be explicit. Price is an integer minor-unit amount from 0 through 2,147,483,647, not floating-point major currency. |
| StorePrinting | Update only | Separate configuration capability for the five fixed printing cases. Partial patches preserve omitted fields, omitted cases and unrelated Store settings; no settings-root access. |
| ProductPrinting | Update only | Separate configuration capability for the boolean `kitchenPrinterEnable`; all other Product settings and ownership remain unchanged. |

Catalog publication, recommendation, price, sold-out state, Counter availability, hierarchy and printing-rule changes have real customer/operational consequences. They do not grant payment, inventory, order-workflow, authorization, credential or external-provider capabilities. Printing configuration is separate from actual print submission; the latter remains unavailable. Arbitrary metadata/settings edits remain excluded outside Content's pre-existing validated policy.

Product hard deletion is unavailable because its mapped Specification cascade exceeds a single-record preview. Specification hard deletion is unavailable because JSON/historical references lack authoritative shared referential-integrity and writer serialization. Other deletion adapters must reject references rather than cascade or silently detach records. Rejected or blocked operations do not justify falling back to generic CRUD requests.

### Printing configuration, not print submission

`StorePrinting` accepts only `order`, `perItem`, `filteredList`, `fullList` and `settlement`. Each supplied case is a non-empty partial object containing only boolean `enabled`, canonical UUID or null `deviceUuid`/`templateUuid`, and integer `copies` from 1 through 100. Omitted references in a patch are resolved from stored state, not invented by the model. Effective enabled cases require valid destination/template references; clearing references is only valid for an effective disabled case. Backend validation checks enabled resources, account availability, Store ownership and matching printer/template kind.

The adapter merges into the current settings instead of replacing the JSON root. Case differences expose only curated printing fields; unrelated settings and private Store data are not included. Effective `after` cases explicitly contain all four fields, including defaults. `ProductPrinting` changes only the kitchen-print flag and preserves other settings, including sale times. The ordinary `Store` and `Product` capabilities still reject settings input.

Saving these configurations creates no print job and calls no provider. It can change automatic printing for future orders, so the confirmation preview must explain that consequence. Printer registration, status refresh, job submission, reprint, template-definition editing and console dispatch are not assistant capabilities. The existing business reprint interface lacks caller-stable deduplication and a durable source association; it must not be invoked through a transactional mutation or an arbitrary endpoint fallback. Business and core modules remain unchanged by this package.

## Chat attachments

User-selected attachments are a separate, explicitly sent model-input channel, not repository access, server file upload, record media editing or an authorization grant. Local preview/selection never sends attachment content. Send captures the files and provider configuration for that task; image submission requires an explicit vision preference, default off. Unsupported inputs fail closed. Only validated local raster data URLs may be submitted as image parts; arbitrary remote image URLs and model-authored tracking images are not enabled.

File counts, byte/pixel limits, the whole serialized provider-request budget and format support are maintained in the [app workflow](../../apps/admin-agent/README.md#images-and-file-input) and owning implementation/tests. Limits apply before provider dispatch, including subsequent tool rounds. Original attachment content is excluded from browser preferences and retained conversation context; only bounded filename summaries survive into later requests. Rendered previews have separate in-page retention bounds and are cleared on conversation/session disposal. Cancellation prevents future dispatch where possible but cannot retract already sent content.

Attachment parsing, filenames and image contents are untrusted data. They cannot supply system instructions, capabilities, endpoints or write confirmation. The model still has prepare-only mutation tools and all existing backend authorization/UI confirmation checks remain in force.

## Curated host knowledge

The generic frontend optionally reads `host.getKnowledgeArticles()`. Missing, throwing, or invalid host data fails closed to no added knowledge. The ns-ultimate host registers articles explicitly under `apps/admin-agent/adapters/ns-ultimate/admin/knowledge/`; no repository scan, remote fetch, or arbitrary file-reading facility is provided. Articles use `{id, title, module, kind, locale, aliases, sourcePath, content}`. Runtime validation bounds article count and field sizes, removes duplicate IDs, and accepts only relative repository-style source paths. Deterministic English-token and Chinese-bigram retrieval selects up to four relevant articles within a shared 18,000-character API-document/knowledge context budget.

Long articles are divided into paragraph chunks of at most 900 characters, split at sentence boundaries when a paragraph is oversized; Markdown headings become section labels. An article contributes at most three chunks (2,000-character excerpt cap), presented in source order, so a broad question keeps context instead of receiving an arbitrary mid-sentence cut. Matched host aliases also supply up to six bounded English terms to the API-document keyword search, which lets a Chinese question match English operation paths and summaries without hardcoding business vocabulary in generic code. No-match queries add no article context.

Selected article excerpts are sent to the configured model provider as untrusted reference data. The UI lists the selected article title, module/kind, and validated source path as plain text; it does not turn source paths into links or navigation targets. Bundled article contents are browser-visible and must be appropriate for the user and model; never put credentials or private operational material in them. Knowledge does not register tools or change query, navigation, mutation, or confirmation policy. Host authors must maintain articles against the owning module docs and implementation; source paths establish provenance, not automatic freshness or correctness.

## Backend protocol

The generic controller requires full authentication. This host mounts it under the existing management security policy; adapters additionally enforce domain permissions on prepare, commit, status and cancel. Operations belong to the stable actor key; other users receive 404 even if administrators. Responses use `Cache-Control: no-store` and the normal admin request client.

| Method and path under `/api/v1/manage/agent/operations` | Behavior |
| --- | --- |
| `POST /` (no trailing slash required) | Prepare `{entity, action, identifier?, changes?}` through a registered adapter. Persists a proposal, not target data. |
| `GET /?page=1` | Current actor receipts only, 20 candidates per page, pages 1–100, newest first by creation time and ID. Returns `{items, page, hasMore}`; inaccessible adapters are omitted, so a page can be short or empty. Also accepts the admin request client transport parameter `_locale` (a bounded locale string), not arbitrary filters or actor overrides. |
| `GET /{operationId}/preview` | Restore the same pending proposal after permission, expiry, canonical payload and snapshot checks; returns a full preview without extending expiry or writing target data. |
| `POST /{operationId}/commit` | Accepts exactly `{confirmed: true}`. Executes only the stored proposal; replacement values are rejected. |
| `GET /{operationId}` | Minimal status/receipt without field values, for recovery after an ambiguous outcome. |
| `POST /{operationId}/cancel` | Invalidates a pending proposal; does not undo a completed mutation. |

Preparation returns `{operationId, entity, action, identifier, title, affectedRecords, expiresAt, differences, saved: false}`; differences contain `{property, before, after}`. Operations affect one target and expire in five minutes. Target identifiers are strings up to 128 bytes; adapters define exact formats. Requests are bounded to 40 KB and full differences to 60 KB. Oversized previews must use the standard editor.

Adapters emit `differences` in their declared field order, not in the caller's key order. MySQL's `JSON` type reorders object keys when a proposal is stored, so an order derived from incoming keys would make a restored preview differ from the original preview on MySQL while matching on SQLite. Field order is therefore part of the adapter's stable output, not a storage artifact.

The Content adapter retains its existing restrictions: title is non-empty and at most 255 characters; body is nullable and at most 20,000 UTF-8 bytes; category/tags reference existing numeric IDs (up to 50 tags); metadata follows the existing schema (`featured`, `layout`); sortOrder is a signed 32-bit integer available only on the business subtype. Other adapters enforce the per-action fields in the business capability table and reuse the existing domain model. These restrictions belong to explicit host adapters, not the generic operation framework. No adapter may trigger receipt printing, payment or other external actions.

Commit rechecks owner, adapter authorization, pending state and expiry, locks the operation row in a transaction, and delegates target locking, conflict detection, revalidation and execution to the adapter. The receipt and domain mutation commit together. Replaying a succeeded operation rechecks permissions and returns the same target without repeating the mutation. Failed read-back verification rolls back the transaction. The Content adapter rejects stale snapshots with 409. Existing unversioned CRUD writers do not participate: this is not a universal optimistic-locking guarantee across every writer. SQLite tests do not validate MySQL lock contention; see the optional MySQL verification in [local development](../operations/development.md) and the recorded result in the assistant README.

An adapter may throw the app-owned `ProposalConflictException` when the target snapshot changed or disappeared, before applying domain mutations. After transaction rollback, commit returns HTTP 409 with `{error: "proposal_conflict", message: "..."}` and `Cache-Control: no-store`. Restore returns the same marker when its snapshot/canonical payload comparison fails or its side-effect-free preparation cannot find the original target. No proposal values or exception details are included. Other 409 errors, permission errors, server errors and missing responses must not be interpreted as this definitive rejection. The operation remains pending in storage until cancellation or expiry; this adds no persisted status or migration.

Counter operation receipts and cancellation remain accessible after target deletion, subject to ownership and current authorization. Restoring or committing a pending proposal whose target was deleted returns a proposal conflict.

## UI lifecycle

The user reviews all differences and explicitly confirms; deletion requires typing `DELETE <identifier>`. A newer message or preview, clearing the conversation, or a session change invalidates the visible pending confirmation. Expiry is checked in UI and backend. Submission is serialized, with no automatic retry after timeout/abort. An explicit `proposal_conflict` response puts the local card in a non-submittable `conflicted` state, explains that the proposal was not saved, and allows discard or a new task without an outcome check. Discard cancels the stored pending operation and erases its values. An ambiguous outcome still offers a status check and blocks new tasks/clearing until resolved. If status is pending, the UI also revalidates the original preview before permitting another explicit confirmation; a conflict disables the old card, and failed revalidation keeps the outcome unknown. Cancellation cannot guarantee reversal after submission starts.

Closing/reloading the page or changing sessions loses the local card, but **Operations** can retrieve the current account's durable receipts and refresh their outcomes without retrying writes. Receipt responses now also include `createdAt` and `expiresAt`; a pending row past expiry is reported as `expired` even before pruning, without changing or erasing its stored payload. Lists never contain proposal values, actor keys or snapshot hashes. Offset pagination is bounded but not a stable snapshot while new operations arrive; refresh page 1 to see new receipts.

Restoring a preview locks and refreshes the stored operation, rechecks adapter authorization and calls its side-effect-free preparation logic with the original payload. It rejects changed snapshots or canonical changes and oversized/empty differences. Only unexpired pending operations are eligible; restoration creates no new operation and requires another explicit UI confirmation, using the original expiry. Commit revalidates independently. These routes add no new migration or adapter interface requirements. Requests are serialized with other assistant activity and aborted on session disposal; values are not stored in browser persistence or supplied to the model. This does not automatically resolve every ambiguous write across browser restarts: users must inspect the durable receipt before manually proposing a replacement.

Authorized API callers and same-origin scripts can invoke the API directly: browser confirmation is an accidental-action safeguard, not proof of human presence against malicious code.

## Migration, retention and validation

Apply `NsUltimate\Apps\AdminAgent\Backend\Migrations\Version20261022120000` through the composed backend workflow. It creates only `admin_agent_operation`, including entity key and string target ID; there are no per-domain operation tables. No environment database is migrated automatically by tests or relocation. The previous uncommitted Content-specific draft migration was not applied in this development session. If another environment applied it, inspect that state and plan a data-preserving conversion first.

Review pending migrations before running `php integration/backend/bin/console doctrine:migrations:migrate`. Schedule `php integration/backend/bin/console app:admin-agent:prune` at least every five minutes and clear composed backend caches after registration changes. Use the integration console, not the core console. The uncommitted draft endpoint `/manage/content-agent/operations` is replaced by `/manage/agent/operations` without a compatibility alias.

Pending proposals retain values in the database. Success and explicit discard erase values, retaining actor, entity, action, field names, target, before-state hash, status and timestamps. Expiry alone does not physically erase values; the pruning command does. Receipts are not a tamper-proof audit ledger, nor are failed requests an exhaustive security audit. Backups, access controls and receipt retention remain deployment responsibilities.

Tests cover multi-adapter dispatch, string IDs, unknown/duplicate keys, authenticated CRUD, conflict detection, idempotency, validation, account isolation, expiry, cancellation, metadata-only pagination, original-proposal restoration, session disposal, migration preservation and client state transitions. Real-backend browser interaction and production-database concurrency verification remain required before deployment.

## Nested configuration inspection (read-only)

This capability explicitly expands the assistant-readable field set for selected records, without granting backend permissions or adding write/navigation capabilities. Selected configuration values are sent to the configured model provider without additional per-read confirmation. The client receives the full authenticated detail response before projection; the 2,000-character cap is a projected-configuration limit, not a transport response-size limit. Returned identity must match the requested identifier; oversized scalar strings are omitted and diagnosed rather than silently shortened.

The generic tool `inspect_record_configuration({entity, identifier})` reads one record's allowlisted configuration scalars through its documented GET detail endpoint (`{collection}/{id}`, where the identifier is an exact positive numeric ID or UUID per the backend detail route). It performs no writes and opens no pages. The generic helper validates arguments (exactly `entity` plus `identifier`; URLs, fields, and JSON paths are rejected), requires the entity in the host-owned inspection policy, requires a readable composed-entity config entry, requires the GET detail route in the loaded OpenAPI document, and then issues one authenticated GET with navigation availability checks, caller cancellation, and a 30-second timeout. The response envelope is unwrapped to a single record carrying identity; collections, malformed, or unexpected-shape payloads fail closed. Only the policy's fixed non-sensitive scalar nested paths are returned; full settings blobs, credentials, record snapshots, and arbitrary metadata never leave the projection. Existing `omitted` remains the count for older consumers; `omissions` adds at most 40 `{path, reason}` entries (`missing`, `null-ancestor`, `invalid`, `oversized`), restricted to validated host-policy paths and at most 2,000 serialized characters. Diagnostics contain no raw values; null scalar leaves, `false`, and `0` remain valid values. Configuration output retains its 2,000-character cap. The UI displays bounded reasons and explicitly distinguishes absent/invalid response fields from permission failures or disabled settings; a successful detail response with omissions is not a backend permission failure. The model must not infer business defaults, device state, or scheduler/worker activity, nor claim a complete root cause from the inspection.

The current host policy owns Store printing configuration (`code`, `name`, `status`, `settings.order.requireAcceptance`, and per-case `enabled`/`deviceUuid`/`templateUuid`/`copies` for the five fixed `settings.printing` cases) and the Product kitchen-print flag (`name`, `status`, `settings.kitchenPrinterEnable`). The OpenAPI-plus-config catalog remains the authority for exposing the capability: the tool is advertised only for policy entities that are readable in the composed catalog, and the detail route is rechecked at execution time. Tests cover policy/method/path/identifier rejection, nested sensitive and prototype-polluting paths, null/malformed projection, secret leakage, unavailable pages, cancellation/timeouts, GET-only transport, and size bounding. Content mutation and Counter name-only mutation are separate explicit host capabilities; neither changes read/inspection policy.
