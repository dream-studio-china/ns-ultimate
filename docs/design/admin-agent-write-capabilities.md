# Admin-agent future write capability matrix

**Approval state: PROPOSED.** This is a research and review artifact only. No capability is granted, enabled, or changed by this document. User approval is required before phase D or any implementation. Printing is explicitly paused and excluded.

## Current boundary

The active host registry contains Content create/update/delete and Counter update of `name` only ([operation contract](../contracts/admin-agent.md#backend-protocol), [host capability descriptions](../../apps/admin-agent/adapters/ns-ultimate/admin/mutation-capabilities.mjs), [service selection](../../integration/backend/config/services.yaml)). Both use the app-owned prepare/confirm/commit protocol. The Counter adapter independently enforces `ROLE_ADMIN`, exact target lookup, name-only payload, trimming/length, conflict checks, and read-back ([CounterMutationAdapter](../../apps/admin-agent/backend/src/Adapter/NsUltimate/CounterMutationAdapter.php)). Content is similarly bounded by its adapter and existing Validator ([ContentMutationAdapter](../../apps/admin-agent/backend/src/Adapter/NsUltimate/ContentMutationAdapter.php)).

The host frontend description is not an authorization grant. Backend authorization, adapter allowlists, the existing domain contract, and tests must all agree. The architecture assigns host-specific mutation policy to `apps/admin-agent/`, with integration explicitly selecting adapters; business rules remain in their owning modules ([architecture](architecture.md#appsadmin-agent), [assistant design](admin-ai-assistant.md#8-risk-policy-preview-and-submission)).

Content service selection is in integration configuration; Counter is explicitly selected in [app service configuration](../../apps/admin-agent/backend/config/services.yaml). Both registrations participate in the composed registry.

## Prioritized candidates for approval

Only the first two are recommended for the next review/implementation batch, and neither is approved. Keep the eventual batch to these two unless the user separately chooses otherwise.

Counter ordering is not verified as staff-only: the current [admin list](../../business/admin/config/collections/counter/Counter.js) defaults to descending ID, while the [public controller](../../business/backend/Counter/src/Controller/Public/CounterController.php) exposes `sort`. Before implementation, establish the persisted integer upper bound and test overflow; do not assume changing `sort` changes every list's order.

## Finite deferred/not recommended candidates

| Candidate | Observed facts and reason not recommended now |
| --- | --- |
| Product `sortOrder` | Project subtype and manage controller expose it; setter touches `updatedAt` ([Product subtype](../../business/backend/Store/src/Entity/Product.php#L13-L38), [controller allowlist](../../business/backend/Store/src/Adapter/ManageProductController.php#L14-L18)). It changes customer-facing ordering and no dedicated validation was found in reviewed code. **Moderate**, not automatically low risk; defer until ordering semantics and numeric bounds are agreed. |
| Product `name` | A product name is customer-facing identity; despite a simple string field, it can alter sales display/search and is not a low-risk generic text edit. **Moderate**; requires explicit bounds/normalization and impact review. |
| Counter `capacity` | Controller requires a positive integer when non-null; `isset` skips null and the setter accepts null. The setter updates timestamp ([CounterController.php](../../business/backend/Counter/src/Controller/Admin/CounterController.php#L74-L79), [Counter.php](../../business/backend/Counter/src/Entity/Counter.php#L67-L70)). Capacity can affect operational seating/assignment. **Moderate/high**; do not bundle with a cosmetic field. |
| Product `category` or `store` | These are associations, not text fields. Product setters enforce store/category scope; controller resolves UUID/ID and rejects disabled categories ([Product.php](../../core/crud-skeleton/src/Store/Entity/Product.php#L91-L119), [ProductController.php](../../core/crud-skeleton/src/Store/Controller/Manage/ProductController.php#L73-L130)). **High**; association moves require separate approval, scope checks, race tests, and impact review. |
| Product `status`, `isSoldout`, `recommendationLevel` | Status changes publication/availability; sold-out and recommendation flags directly affect customer experience. Values are explicit in the project form/subtype ([product.jsx](../../business/admin/config/overrides/product/product.jsx#L188-L196), [Product.php](../../business/backend/Store/src/Entity/Product.php#L41-L69)). **Moderate/high**; not a routine description edit. |
| Product price/specifications | Nested specification manager exposes `name`, `price`, `sort` and separate create/edit flows ([product.jsx](../../business/admin/config/overrides/product/product.jsx#L35-L179)). Price is explicitly consequential; nested relation mutation is not a single scalar update. **High**; separate approval and complete workflow tests required. |
| Common Category/Tag records | Entities exist in the upstream core, but this review found no project-owned business controller/config for editing those records. Content's current adapter only uses existing Category/Tag IDs when changing a Content record. Do not infer write support from entity existence. **Unresolved/not a candidate** absent a verified composed route, authorization contract, and ownership decision. |

## Explicit exclusions

No proposals here authorize payment or refund, inventory/stock, order or fulfillment state, printing/reprint/device operations, bulk/multi-record writes, authentication or authorization changes, credentials/secrets, metadata/settings/JSON blobs, association moves, or deletion. Treat each as excluded until independently reviewed and expressly approved. Product price and inventory are not low-risk. Printing remains **PAUSED** and excluded, including indirect custom actions.

## Review caveats and approval gate

- These findings describe inspected repository source, not a guarantee about every deployed route, role assignment, database state, or dynamic configuration. No database/provider calls or secret values were inspected.
- Controller attributes and accepted-property lists establish observed route-level checks, not proof of all deployment authorization wiring. Verify effective role grants and request behavior in deterministic integration tests before enabling any candidate.
- Search found no Product description-specific listener or external effect in the reviewed business source; dynamic hooks, deployment overrides, database triggers, and uninspected consumers remain unresolved. Absence from this search is not proof of absence.
- A later phase must change only app-owned host policy/adapter and tests unless a separately authorized scope says otherwise. Do not edit core or business merely to make a candidate fit; report blockers for approval.
- Approval must name the exact entity, action, fields, user role/scope, and side-effect/risk acceptance. Until then, keep the registry unchanged and the candidates unavailable.
