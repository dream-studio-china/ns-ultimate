# Promotion business adapter

`PromotionDateService` decorates the existing Core promotion service. It fixes only campaign `startTime` and `endTime` writes through the existing administrator promotion API; it does not replace routes, authorization, entities, pricing strategies or the general Core date mapper.

- Calendar dates (`YYYY-MM-DD`), Admin picker timestamps (`YYYY-MM-DD HH:mm:ss`) and ISO-8601 timestamps are converted to `DateTimeImmutable` before delegation.
- Explicit `null` clears the supplied boundary; omitted fields remain unchanged. Empty strings, relative dates, invalid types and invalid calendar dates are rejected as HTTP 400 before date mutation.
- Explicit timezone offsets are normalized to the PHP application timezone before storage because the existing Doctrine `datetime_immutable` column does not retain timezone information. Inputs without an offset use that same application timezone; clients should send offsets when specifying local Store times.
- The original persistence, validation, transaction and `noFlush` behavior is retained. This adapter does not add a start-before-end rule or alter active-window matching, percentage rounding, stacking or exclusivity.

Business controller substitutions reuse the upstream customer and administrator Order controllers, including their authorization, ownership filters, CRUD actions and transitions. The shared `OrderPromotionCreation` hook explicitly passes the current creation's pricing result into `metadata._promotion` before the inherited `processEntity` calls `createOrder`. It quotes once; no service remembers a previous quote, matches fingerprints or correlates requests. Currency checks are retained; malformed non-list items and non-object item entries are rejected as HTTP 400 before pricing. Staff orders and customer Counter merges explicitly pass their own pricing result at their creation call sites. Direct service consumers must do the same; merely calling `calculatePrices` has no persistence side effects.

- The snapshot is stored under `trade_order.metadata._promotion` and contains only `applied[{id, name, type, phase}]` plus `recordedAt`. The raw pricing meta, promotion configuration and candidates are not persisted.
- `phase` is `inner`, `outer` or `best_price`. Orders created before the snapshot existed have no key, which the admin renders as "Not recorded" rather than "No promotion used".
- Customer and administrator create flows replace caller-supplied `_promotion` with the current quote. Administrator draft metadata updates preserve the stored key, including when metadata is cleared, and strip forged keys on legacy orders. Other metadata retains the existing replacement semantics. Staff metadata validation already rejects keys beginning with `_`; staff replacements discard inherited snapshots. These are guarantees of the listed entry points, not a new entity-level immutability rule for every internal metadata writer.
- Per-promotion discount amounts are not recorded because the pricing meta does not itemize them. The admin UI lists campaign name, calculation phase and type only. Inner/outer are execution stages, not item/order targeting guarantees (an inner-stage campaign can reduce the whole order).

No migration or Core edit is required. The integration Kernel discovers this module by convention; rebuild the application container during normal deployment. Tests cover the composed administrator API and service delegation against an isolated database. No production data is modified by the fix or its tests.

## Admin assistant

Promotion and PromotionTemplate retain their ordinary CRUD, with a required template relation, four conflict modes and supported type/phase selects. `PromotionDraftWorkbench` and its administrator-only controller add non-persistent draft validation and single-rule simulation using the existing parser/evaluator/strategies. `PromotionStackSimulator` and its controller add read-only multi-campaign simulation through the real `PromotionCalculator` for currently eligible store campaigns, selected campaigns or validated in-memory drafts. No assistant-specific backend package or pricing engine is introduced. The browser adapter provides deterministic recipes and requires passing expected-result samples for campaign proposals before normal UI-confirmed CRUD submission.

Parameter contracts can be stored in template `fields`; campaign `config` uses actual DSL/strategy inputs, including custom names, instead of the retired fixed frontend parameter schema. Legacy unsupported field formats and extensions require manual review. This does not change ordinary CRUD persistence validation. See the [promotion authoring contract](../../../docs/contracts/promotion-authoring.md) for payload semantics, units, stack simulation modes and limitations, and the [assistant guide](../../../apps/admin-agent/README.md#promotion-management) for the authoring workflow.
