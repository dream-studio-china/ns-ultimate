# HuifuFin Store payment adapter

`HuifuFin` owns Huifu provider credentials, merchant profiles, Store bindings,
payment attempts, refunds, signed notifications, reconciliation, and POS receipt
intake. It is a conventional business module discovered from
`business/backend/HuifuFin/src/`; it is not a Symfony bundle class.

## Setup

1. Set `HUIFU_CONFIG_KEY` to a private, stable value before creating provider
   profiles. It encrypts RSA private keys and notification secrets at rest.
   Changing or losing the key makes stored credentials unreadable.
2. Set `HUIFU_API_BASE_URL` for production and, if used,
   `HUIFU_SANDBOX_API_BASE_URL`. Sandbox calls fail closed when the URL is empty.
3. Configure `DEFAULT_URI` to the public backend origin. Huifu notification URLs
   are generated by Symfony's URL generator and must be reachable by Huifu.
4. Run migrations.
5. Run `php bin/console app:huifu:seed-authorization` to create the Store-scoped
   permissions and the `store_huifu_manager` role.
6. Create a provider profile, merchant, Store grant, and Store setting through
   the Admin UI or the management API.

The `.env.test` values are test-only. Do not reuse production credentials in
tests or commit private keys.

## Configuration hierarchy

```text
HuifuProviderProfile (sys_id, product_id, signing credentials)
    -> HuifuMerchant (huifu_id, capabilities)
        -> HuifuMerchantStoreGrant (Store access)
            -> StoreHuifuSetting (methods, default method, POS switch)
```

Several Stores can share one merchant or use different merchants. A Store
member can select only a merchant explicitly granted to that Store.

Credentials are never returned by the API. Provider identity (`sysId`,
`productId`) and the merchant `huifuId` are separate because the API access
identity is not necessarily the merchant receiving funds. Rotating credentials
creates a new encrypted credential version; payment attempts and refunds keep
using the version recorded at initiation. Environment, system ID, and product ID
are immutable after profile creation; create a new profile instead of repointing
historical attempts. Credentials and descriptive fields remain editable.

## Online payment

Signed-in customer initiation uses the unified `POST /api/v1/app/orders/{id}/payment`
with `payment: huifu`, `gateway: native|jspay|quickpay` and an optional matching `tradeType`.
It supports the order owner and globally enabled third-party payment without
employee Store permissions. It reuses the composed Trade preparation checks and
the Huifu attempt/proof pipeline, with an explicit commit boundary before any
provider call. See the [customer payment contract](../../../docs/contracts/huifu-customer-payments.md)
for payer identity, launch data, unknown outcomes and retry limitations. The
public order payment GET remains read-only. Customer tests simulate provider
responses/notifications only; real merchant/browser acceptance remains required.

Payment initiation goes through:

```text
POST /api/v1/store/{scopeId}/huifu-payments
{"invoiceUuid": "...", "channel": "jspay|native|quickpay", "tradeType": "T_JSAPI|T_NATIVE"}
```

The Store payment service creates a committed `HuifuPaymentAttempt` before
calling the Core invoice workflow. The `huifu` gateway requires that attempt
identifier and refuses unsupported generic calls. This preserves a request
record when the provider result is unknown. Only one attempt may await
confirmation per invoice; a timeout leaves the attempt `unknown` and blocks a
replacement until reconciliation or an operator resolves it. Stale `created`
attempts enter reconciliation after five minutes. The Store endpoint supplies a
short-lived internal proof, so the generic Core pay route cannot submit or
resume a Huifu attempt.

The initial implementation supports Huifu JSAPI and Native order creation. Quick
pay is stored and submitted, but quick-pay refunds are intentionally rejected
until the product-specific endpoint is validated. WeChat JSAPI requires the payer
to have logged in through the Store's configured WeChat application; the OpenID
is resolved server-side.

A successful order-creation response leaves the invoice in `paying`. Only a
verified notification or reconciliation query marks it paid.

## Notifications

```text
POST /api/payment/notify/huifu/{attemptUuid}
POST /api/payment/notify/huifu-pos/{merchantUuid}
```

Payment notifications use the attempt UUID in the callback path so the server
can select the original provider profile and credential version. The service
verifies the signature, merchant, request sequence, amount, currency, and Store
association, then applies the result through Core's invoice service.

Rejected notifications keep the generic HTTP 400 `FAIL` response so Huifu
retries and callers learn nothing. The precise reason, request fields, outbound
provider request/response and the generated `notify_url` are written to the
project audit log. See the [API audit logging guide](../../../docs/operations/audit-logging.md)
for the file location, rotation and lookup commands.

Duplicates are acknowledged without emitting a second payment event. The attempt
is locked and reloaded before applying a result, so a concurrent notification or
reconciliation query cannot downgrade a confirmed payment. A conflicting
notification is recorded and acknowledged for operator review.
Synchronous provider responses must be signed, and unsigned responses are
treated as an unknown result rather than a failure. A notification for a
cancelled invoice is rejected and requires operator review. The legacy public
signing endpoint is not reproduced.

The implemented notification format uses the legacy `resp_code`, `resp_data`,
and `sign` form fields with RSA verification. Confirm the exact protocol for the
contracted Huifu product before enabling production callbacks; the official SDK
also documents a different webhook-key variant.

## Refund

```text
POST /api/v1/store/{scopeId}/huifu-refunds
{"invoiceUuid": "...", "amount": 1000, "reason": "..."}
```

Integer amounts are cents; decimal strings are also accepted. A refund record is
committed before submission, and concurrent requests reserve the remaining
amount under an invoice lock. Huifu acceptance is not treated as a completed
refund. Only a confirmed success is applied to Core, exactly once; otherwise the
endpoint returns HTTP 202 and the reconciliation command retries the query.
Confirmed refunds that were not yet applied to Core are also retried.

The generic Core refund endpoint cannot create an untracked Huifu refund. The
gateway requires the HuifuFin refund identifier and the internal workflow proof,
so a confirmed record cannot be consumed directly through the generic route.
Only a confirmed record is returned to Core. Refunds use the original payment's merchant, request date,
request sequence, and credential version.

### Core refund transaction boundary

The refund workflow calls the Core invoice-source policy under the same
source-before-Invoice lock order before sending a new provider refund request.
For Trade invoices this rejects a non-paid order or a different linked Invoice
before any Huifu request is made. The Core policy still rechecks eligibility
when applying the confirmed result.

Refund entry points (`request`, `refresh` and `applyToCore`) must run without a
caller-owned outer transaction. Applying an already-confirmed Huifu refund uses
three boundaries: a short transaction reloads and validates the Huifu record;
Core then owns its refund reservation/finalization transactions; a final short
transaction marks `coreApplied`. No Huifu application lock spans the Core call.
Core's reservation-before-side-effects guard is not bypassed.

The stable Core `idempotencyKey` is `huifu-refund:<refundUuid>`. If Core commits
but marking `coreApplied` fails, reconciliation retries with the same key and
recovers the completed Core result before marking the local record. This must
not add the refund amount twice, dispatch another refund event, or submit a
second provider request. Concurrent processing may require retry/reconciliation
rather than a new refund key. Do not manually change the key to clear an
unresolved Core refund attempt.

Isolated tests cover partial application/replay, recovery after a committed full
refund with a missing local marker, outer-transaction rejection, and source-policy
rejection before provider submission. They do not establish real provider or
MySQL concurrency behavior.

The refund query endpoint is implemented from the product's scan-pay family. It
must be verified against the actual contracted product before production use.

## POS

`HuifuPosDevice` maps a terminal to one merchant and Store. POS notifications are
verified, deduplicated by provider transaction ID, and stored as
`HuifuPosReceipt`.

If `req_seq_id` matches a store-scoped invoice and the amount matches, the receipt
is linked and the invoice is marked paid. Otherwise the receipt is retained as
`unclaimed`. The adapter does not automatically create wallet deposits or choose
a target user. `linked_order` and `unclaimed` modes are recorded for operator
policy but do not bypass this default.

## Reconciliation

```sh
php bin/console app:huifu:reconcile --limit=50
```

The command queries due payment attempts and refunds. Timeouts and ambiguous
responses remain `unknown` until query confirms or the operator handles them.
Schedule it through the deployment's existing scheduler; the repository does not
start a scheduler automatically.

## Permissions

The seed command creates:

- `store:huifu_setting:read`, `create`, `update`, `delete`;
- `store:huifu_payment:read`, `create`;
- `store:huifu_refund:read`, `create`;
- `store:huifu_pos_receipt:read`.

Store endpoints require active membership and the matching scoped permission.
Platform credential and merchant management remains admin-only.

## Validation

```sh
make test-backend
make type-check
npm run validate:configs --prefix core/crud-admin
```

The integration tests use an isolated SQLite database and a fake Huifu client.
They cover encrypted configuration, multi-Store sharing and isolation, signed
payment notification idempotency, refund confirmation, POS receipt deduplication,
and unknown-terminal rejection. They do not establish live Huifu API, sandbox,
callback-network, MySQL-concurrency, or production-refund behavior.

## Not implemented in this release

- Huifu account onboarding, profile synchronization, balance, transfer, and
  withdrawal;
- automatic POS wallet top-up;
- quick-pay refunds and a verified quick-pay query contract;
- POS-linked invoice refunds; POS receipts are recorded and linked, but the
  refund workflow only handles online `huifu` payments;
- automatic provider close when an invoice is cancelled;
- a refund notification endpoint distinct from the query workflow;
- a scheduler process, provider dashboard, or operator exception queue UI.
